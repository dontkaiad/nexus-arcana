# ADR-0027 — Домен «Люди»: таблица `people`, `memories.person_id`, модерация фактов через `review_status`

**Date:** 2026-10-19
**Status:** Accepted — PR-1 (схема + фильтр чтения). Резолв упоминаний, импорт, API и UI — следующие PR.
**Domain:** `core/repos` (memories, people), `core/memory.py`, `core/memory_rag.py`, Alembic `*_people_domain`
**Relates to:** [ADR-0005](0005-memory-store.md) (хранилище памяти), [ADR-0020](0020-memory-rag.md) (эмбеддинги на `memories`), [ADR-0021](0021-memory-rag-reranking.md)

## Контекст

Факты о людях живут в 🧠 Памяти как строки `memories` со свободной связью
`related_to` («имя | алиас | …»). Это работает для ILIKE-поиска, но:

- у человека нет собственной сущности: день рождения, tg/vk-идентификаторы,
  алиасы и заметки размазаны по фактам;
- массовый импорт из переписок (tools/people_import) порождает сотни
  автоизвлечённых фактов, которые нельзя пускать в контекст ботов, пока их
  не проверил человек;
- слияние двух записей одного человека невозможно без правки текстовых полей.

## Решение

### 1. Таблица `people`

`id, user_id, name, aliases text[], birthday date, tg_id, tg_username, vk_id,
notes, status pending|confirmed, created_at, updated_at`.

- **Нет unique на `name`**: однофамильцы и тёзки законны. Идентичность задают
  только внешние id: частичные unique `(user_id, tg_id) WHERE tg_id IS NOT NULL`
  и `(user_id, vk_id) WHERE vk_id IS NOT NULL`.
- `aliases` — массив с GIN-индексом (алиасов мало, читаются вместе с человеком;
  отдельная таблица — лишний join).
- Owner-ключ `user_id` как во всех доменах (#144, #202).
- Это НЕ heylark-`people (tg_id, display_name)` из `core/auth_grants.py`: та
  таблица живёт в отдельной БД `auth` (ADR-0026) и к этой не относится. Коллизии
  на уровне БД нет, но имя в коде совпадает — модули не смешивать.

### 2. `memories.person_id` и `memories.review_status`

- `person_id bigint NULL REFERENCES people(id) ON DELETE SET NULL` — удаление
  человека не удаляет факты, а отвязывает их.
- `review_status text NOT NULL DEFAULT 'confirmed'`, CHECK
  `pending | confirmed | rejected`. Существующие строки получают `confirmed` от
  дефолта, поэтому видимое ботам множество памяти после миграции не меняется.
- Отдельная колонка, а не `is_current`: тот уже означает «актуально/устарело»
  (деактивация пользователем), смешивать два смысла нельзя.

### 3. Эмбеддинги остаются на `memories` (ADR-0020)

Вектор по-прежнему колонка `memories.embedding`, `people` его не получает.
Семантический поиск по-прежнему идёт по фактам; `people` — справочник для
резолва упоминания в `person_id` (следующий PR), а не второй векторный индекс.

### 4. Правило чтения: везде только `confirmed`

Любое чтение для контекста и поиска видит только `review_status='confirmed'`:
ILIKE-поиск (`_search_sync`, оба режима `match_all`), списки по категории и
недавние, поиск по префиксам и точному ключу, семантический SQL
(`memory_rag.search_memory_semantic`), `get_memories_for_context`, команда
`/memory`, Mini App `/api/memory`. Фильтр сидит в слое репозитория
(`confirmed_only=True` по умолчанию), чтобы новый вызывающий код не мог его
забыть.

**Деструктивные операции без изменений:** «забудь»/«удали» вызывают поиск с
`confirmed_only=False` и могут убрать pending-факт.

### 5. День рождения — только `people.birthday`

Факты-«ДР» в `memories` не создаются: единственный источник — колонка
`people.birthday`. Это снимает расхождение между фактом и полем и убирает
birthday-ключи из памяти.

### 6. Проверка — только в Mini App

Модерация (approve/reject факта, подтверждение человека, слияние) — в
Mini App. Промежуточное одобрение в `people_staging.jsonl` (`approved=true`)
убирается в PR-2: staging остаётся буфером извлечения, но не вторым этапом
ревью.

### 7. Импорт (PR-2): правила идентичности

- Жёсткие ключи — `tg_id` / `vk_id` (id чата из TG-экспорта, peer_id из VK-архива,
  id из API). Одноимённые люди с разными id остаются разными людьми; ключ факта —
  `person_{person_id}_{type}_{hash8}` по id, а не по slug имени.
- Автосклейка VK↔TG только при совпадении нормализованных имени+фамилии
  (одного имени недостаточно) И (одинаковый ДР ИЛИ `tg_username == vk screen_name`),
  и только если совпадение взаимно-однозначное. Остальное остаётся отдельными
  pending-людьми — склеивает человек через merge.
- Строки без id привязываются только к единственному id-кандидату того же
  источника с тем же именем; при нескольких — отдельный id-less человек.
- Человек без фактов и без ДР не создаётся.
- ДР: API → `people.birthday`; ДР из переписки — только если дату удалось
  распознать однозначно и поле пусто. Существующее `birthday` не перезаписывается
  (ручная правка в UI побеждает повторный импорт). **Год неизвестен → 1904**
  (високосный, чтобы 29.02 было валидно); потребители обязаны считать 1904
  «года нет» и не вычислять по нему возраст.
- Факты пишутся с `review_status=pending`, `source=auto`; повторный upsert по
  ключу НЕ откатывает подтверждённый/отклонённый факт в pending. В текст факта
  добавляется имя, если его там нет («любит чай» без субъекта бесполезно в
  контексте бота). Эмбеддинги — пачками (`index_memories_batch`), по одному
  запросу Voyage на пачку, с паузой под лимит.

### 8. API Mini App (PR-4) и явный флаг года

- `people.birthday_year_known boolean` вместо неявной заглушки: при `false` в
  `birthday` лежит 1904, а API отдаёт `--MM-DD` и `age=null` (`core/people.age()`
  возвращает `None` без года). Заглушка наружу не утекает.
- `people.status` допускает `rejected` (`reject-all`). Список по умолчанию
  скрывает `rejected`, показывает при явном `?status=rejected`.
- `/api/people`: список (сортировка по числу pending-фактов), карточка (факты
  группами `important → likes → dislikes → other`), PATCH, approve/reject факта,
  approve-all/reject-all (меняют и `status` человека). Тип факта выводится из
  `key_name` (`person_{id}_{type}_{hash8}`); ручные факты считаются `other`.
- Чужая или несуществующая запись всегда 404 (не 403), владелец —
  `current_user_id → user_id`.

### 9. Дубли и merge (PR-5)

- `GET /api/people/duplicates` — только подсказка, ничего не склеивает. Сигналы:
  совпавшая пара имя+фамилия (порядок слов не важен), общий токен имени + одинаковый
  ДР (годы сравниваются, только если известны у обоих), алиас одного = имени другого.
  `score = 1 − Π(1 − w)`; пары с разными `tg_id` (или `vk_id`) — разные аккаунты,
  в кандидаты не попадают; `rejected` пропускаются.
- `POST /api/people/{id}/merge {into_id}` — одна транзакция, `id` удаляется. Факты
  переезжают на цель, ключ `person_{id}_{type}_{hash8}` переписывается на id цели;
  при совпадении ключа остаётся **целевой** факт, источника — удаляется. Алиасы —
  union (имя источника тоже становится алиасом), пустые поля цели заполняются из
  источника, различающиеся заметки склеиваются. Имя и статус цели не меняются.
  У обоих разные `tg_id`/`vk_id` → 409: потерянный id при повторном импорте
  воскресил бы дубль.
- Повторный импорт после merge идемпотентен: id-less строка без id матчится с
  человеком по id-less имени/алиасу или, для человека с id, только по алиасу
  (так выглядит склеенный источник); совпадение одного имени с id-человеком
  склейкой не считается.

## Рассмотренные альтернативы

- **`is_current=false` для непроверенных** — отвергнуто: конфликт с
  пользовательской деактивацией, ломает «неактуальные» списки.
- **Отдельная таблица `pending_facts`** — отвергнуто: дублирует схему
  `memories`, двойной RAG-индекс и дрейф при approve (ADR-0020 по той же причине
  отказался от зеркальной таблицы эмбеддингов).
- **Unique на `(user_id, lower(name))`** — отвергнуто: тёзки законны, слияние
  делается явно (merge), а не констрейнтом.
- **Алиасы отдельной таблицей** — отвергнуто (см. п. 1).

## Последствия

- Pending-факт невидим для ботов, пока не подтверждён; подтверждение — только
  через UI (PR-4/PR-6), до этого импортированное «не работает» намеренно.
- Забывчивый путь чтения не сможет протечь: дефолт параметра — `True`.
- Миграция аддитивная и обратимая; прод-проверка — равенство числа видимых
  памятей до и после.
